# 第 03 课：JVM 内存结构与垃圾回收

> 本课目标：认识 JVM 的内存分区，理解垃圾回收（GC）的原理，最终能解释"为什么 Minecraft 会突然卡一下"。
>
> 前置知识：本模块第 01、02 课。

## 3.1 JVM 的内存地图

JVM 启动后会向操作系统要一大块内存，然后自己规划成几个区域，各司其职：

```
┌──────────────────────── JVM 管理的内存 ────────────────────────┐
│                                                                │
│  堆（Heap）                    ← 最大的一块，所有 new 出来的对象  │
│  ├─ 年轻代（Young）              都住这里。GC 的主战场            │
│  │   ├─ Eden（伊甸园）                                         │
│  │   └─ Survivor（幸存者区）                                    │
│  └─ 老年代（Old）                                               │
│                                                                │
│  栈（Stack，每个线程一份）       ← 方法调用、局部变量             │
│                                                                │
│  元空间（Metaspace）            ← 类的"图纸"信息（类结构、方法）   │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 堆（Heap）：对象的城市

每次 `new Sword()`、`new ItemStack(...)`，对象都在堆里安家。Minecraft 世界里有海量对象：每个实体、每个物品堆、每个粒子……堆是给游戏分配内存时的主体（启动参数 `-Xmx4G` 说的就是最大堆 4GB）。

### 栈（Stack）：方法的"工作便签"

每调用一个方法，JVM 就在当前线程的栈上压入一个"栈帧"，里面放这个方法的**局部变量**；方法返回，栈帧弹出。

```java
void a() { int x = 1; b(); }    // x 在 a 的栈帧里
void b() { int y = 2; }         // y 在 b 的栈帧里；b 结束后 y 自动消失
```

栈的特点是**后进先出、自动清理**——方法一结束，局部变量就消失，不需要 GC 操心。递归太深会把栈撑爆，就是著名的 `StackOverflowError`（栈溢出）。

### 元空间（Metaspace）：类的档案室

类加载时，类的结构信息（方法表、字段表、常量池等）放在元空间。模组越多、类越多，元空间越大。

> 💡 一张图记住堆和栈的区别：
> - **堆**：`new` 出来的对象，大家共享，GC 管理，容量大；
> - **栈**：方法里的局部变量，每个线程私有，随方法调用自动生灭，容量小。

## 3.2 垃圾回收（GC）：自动回收站

### 什么是垃圾？

```java
Sword sword = new Sword("铁剑", 6);
sword = null;   // 没人再指向这把剑了——它成了"垃圾"
```

C 语言要程序员手动 `free` 内存（忘了就内存泄漏）；Java 中**没人引用的对象由 GC 自动回收**——这是 Java 最大的卖点之一。

### GC 怎么判断"垃圾"？

**可达性分析**：从一组"根对象"（正在运行的方法的局部变量、静态变量等）出发，沿着引用链能摸到的对象都是"活的"；摸不到的就是垃圾。

```
静态变量 ──→ 背包 ──→ 物品1 ──→ 附魔数据    （都活着）
                    
旧剑对象（谁也不再引用它）                    （垃圾，回收）
```

> 💡 **类比**：GC 像查户口。从"根"出发沿着"谁认识谁"的链条走访，走访不到的房子就是空屋，拆除回收。

### 分代回收：为什么要分年轻代和老年代？

JVM 统计发现一个规律：**绝大多数对象朝生暮死**（比如每次渲染创建的临时对象），少数对象长命百岁（如玩家数据）。于是把堆分成两代，区别对待：

```
new 对象 → 先进 Eden 区
              │
Eden 满了 → 触发 Minor GC（小扫除，快）
              │ 还活着的 → 搬进 Survivor 区
              ▼
在 Survivor 里熬过几次 GC → 晋升老年代（Old）
              │
老年代满了 → 触发 Major/Full GC（大扫除，慢，卡顿元凶）
```

- **Minor GC**：只扫年轻代，快（毫秒级），频繁；
- **Full GC**：扫整个堆，慢（可能上百毫秒甚至更久），期间游戏线程可能被暂停——**这就是 Minecraft 偶尔"卡一下"的常见原因**（俗称 GC 停顿 / Stop-The-World）。

### 内存溢出：OutOfMemoryError

如果对象太多太活跃，堆满了 GC 也清不出空间，游戏崩溃并报 `java.lang.OutOfMemoryError: Java heap space`。模组装太多、内存分配太少时常见。解法见第 05 课的调优。

## 3.3 把知识接回 Minecraft

| 现象 | 本课的解释 |
|---|---|
| 游戏玩着玩着突然卡半秒 | 多半是一次 Full GC 停顿 |
| 装 200 个模组后报 OutOfMemoryError | 堆（或元空间）不够用了 |
| 分配 32GB 内存反而更卡 | 堆太大 → Full GC 一次要扫的对象更多 → 停顿更长（内存不是越大越好！） |
| 实体太多时帧数暴跌 | 大量对象在堆里生灭，GC 压力山大 |

---

## 3.4 本课小结

- JVM 内存主要分区：**堆**（对象，GC 管理）、**栈**（局部变量，自动生灭）、**元空间**（类信息）。
- GC 用可达性分析找垃圾：从根对象出发摸不到的对象就被回收。
- 堆分年轻代/老年代：Minor GC 快而频繁，Full GC 慢且会造成卡顿停顿。
- 内存不是越大越好；模组装太多要适度增加 `-Xmx`。
