# 第 02 课：类加载机制——类是怎么"进"JVM 的

> 本课目标：理解类的生命周期与双亲委派模型，明白 Forge 如何用类加载器组织几十个互不干扰的模组。
>
> 前置知识：本模块第 01 课、模块二第 04 课（反射）。

---

## 2.1 类的生命周期：从出生到死亡

一个类从 `.class` 文件到被 JVM 使用，要过五关：

```
加载(Loading) → 验证(Verification) → 准备(Preparation)
    → 解析(Resolution) → 初始化(Initialization) → 使用 → 卸载
```

重点理解三个：

1. **加载**：找到 `.class` 文件（可以在 jar 里、网络里、甚至动态生成），把字节码读进 JVM；
2. **验证**：检查字节码是否合法、安全（比如有没有越界访问内存的指令）——JVM 是"带安检的运行环境"；
3. **初始化**：执行类的**静态代码块和静态变量赋值**。这时候 `public static final String MODID = "mycoolmod"` 才真正被赋上值。

> 💡 **类是"懒加载"的**：一个类只有在**第一次被主动使用**时（第一次 new、第一次访问静态成员）才会被加载和初始化。启动时 JVM 不会把所有类都搬进来——Minecraft 有几万个类，全加载要等天亮。

## 2.2 ClassLoader：类的"搬运工"

**类加载器（ClassLoader）** 是负责"加载"环节的组件。JVM 自带三层加载器，呈父子关系：

```
启动类加载器（Bootstrap）      ← 加载 Java 核心类（String、List 等，最信任）
    ↑ 父亲
扩展/平台类加载器（Platform）   ← 加载 JDK 扩展类
    ↑ 父亲
应用类加载器（App/System）      ← 加载你的程序类路径（classpath）下的类
```

### 双亲委派模型（Parent-Delegation）

加载一个类时的规则：**先问爸爸，爸爸搞不定我才自己来**。

```
收到"加载 com.example.Sword"的请求
    │
    ▼
问父加载器："你加载过吗？你能加载吗？"
    │
    ├── 能 → 父加载器加载，完事
    └── 不能 → 我自己尝试加载
```

这样设计的好处：

- **安全**：你自己写了个 `java.lang.String` 想搞破坏？双亲委派会优先用 Bootstrap 加载正牌 String，你的冒牌货根本没机会上场；
- **不重复**：一个类在 JVM 里只被加载一次（由同一个加载器）。

> ⚠️ 注意：JVM 判断两个类是否"相同"，看的是 **类全名 + 加载它的类加载器**。同一个类被两个不同的加载器加载，在 JVM 眼里是两个不同的类！这点对理解模组隔离至关重要。

## 2.3 Forge 的类加载魔法：几十个模组如何共处一室

你的游戏 `mods` 文件夹里可能有 50 个模组，每个都是独立 jar，里面可能有**同名类**（两个模组都写了 `Utils.class`）。它们怎么不打架？

答案：**Forge 为模组使用了独立的类加载器**（TransformingClassLoader 等自定义加载器）。大致结构：

```
JVM 启动
  └─ 系统类加载器：加载 Forge 本体
       └─ 模组类加载器：按顺序加载 mods/*.jar 里的类
            ├─ 模组A 的类
            ├─ 模组B 的类
            └─ 你的模组类
```

这套机制解决了几个问题：

1. **隔离**：各模组通过委托规则互不污染；
2. **转换（Transform）**：Forge 的类加载器在加载类的过程中能**修改字节码**——这就是"核心模组（coremod）"和 Mixin 技术的入口（第 04 课讲）；
3. **发现**：扫描 jar 里的 `@Mod` 注解（反射的前提是类已可加载）。

> 💡 现在回看第 05 课的"模组生命周期"：所谓"扫描并构造模组对象"，底层就是类加载器把 `@Mod` 类加载进来，Forge 再用反射 `newInstance()`。

### 一个你能亲眼看到的现象

游戏崩溃报告（crash report）里经常有：

```
java.lang.NoClassDefFoundError: com/somepackage/SomeClass
    at ...
Caused by: java.lang.ClassNotFoundException
```

翻译成人话：**类加载器想加载某个类，但翻遍所有 jar 都没找到**。常见原因：模组版本不配套、缺前置模组、或把只在客户端存在的类拿到了服务端用（模块二第 02 课的 Dist 问题——现在你知道它的底层原因是类加载失败了！）。

## 2.4 动手实验：观察类加载

JVM 提供参数让你"看到"类加载过程。用下面命令运行一个普通 Java 程序：

```powershell
java -verbose:class HelloJava
```

输出里每一行 `[class,load] xxx` 就是一个类被加载的记录。你会惊讶：一个打印 hello 的小程序居然加载了上千个类！

在 runClient 的启动日志里也能看到 Forge 加载模组类的过程（搜索 `modid` 或你的包名）。

## 2.5 本课小结

- 类的生命周期：加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载；类是**懒加载**的，第一次使用时才初始化。
- 类加载器呈父子层级，遵循**双亲委派**：先让父加载器尝试。保证安全和不重复。
- 类的身份 = 类全名 + 类加载器。不同加载器加载的同名类是不同的类。
- Forge 用自定义类加载器加载模组 jar，实现隔离、字节码转换和模组发现。
- `NoClassDefFoundError` / `ClassNotFoundException` 的本质：类加载器找不到类。
