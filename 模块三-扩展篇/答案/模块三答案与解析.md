# 模块三 · 答案与解析

> 先独立完成练习和实验，再来看答案。

---

## 第 01 课答案

**1.** `.java` 是源代码，由人编写；`.class` 是字节码，由 javac 编译 `.java` 产生，交给 JVM 执行。字节码不是 CPU 直接能执行的机器码，需 JVM 翻译。

**2.** JDK ⊃ JRE ⊃ JVM：JDK = JRE + 开发工具；JRE = JVM + 标准类库。

**3.** 因为 jar 里是平台无关的字节码，各操作系统上有各自的 JVM 实现负责把字节码翻译成本机机器码——"一次编写，到处运行"。

**4.** 解压 jar 能看到：你的类编译成的 `.class` 文件（按包目录组织）、`assets/` 资源目录、`META-INF/mods.toml`、`pack.mcmeta` 等。说明 jar 的本质就是一个 zip 压缩包，打包了"字节码 + 资源 + 元数据"，作为模组的分发单元。

**5.** 输出示例（`System.out.println` 一个字符串）中可能看到：`getstatic`（取 System.out 静态字段）、`ldc`（加载字符串常量）、`invokevirtual`（调用 println）、`return`。能认出这几个即可。

**6.** 不会。JIT 编译本身要消耗资源（编译线程、缓存空间），对只执行一次的代码做编译是亏本买卖——翻译成本超过了逐条解释的成本。所以 JVM 只对"热点"（执行次数超过阈值的代码）投入编译，这是典型的"把资源花在刀刃上"的成本收益设计。

## 第 02 课答案

**1.** 加载 → 验证 → 准备 → 解析 → 初始化（之后是使用和卸载）。

**2.** 双亲委派：类加载请求先委托给父加载器处理，父加载器无法完成时才由自己加载。好处：① 安全——核心类（如 java.lang.String）永远由最顶层的可信加载器加载，无法被伪造替换；② 避免重复加载——同一个类在体系中只被加载一次。

**3.** 类的身份 = 类全限定名 + 加载它的类加载器。不同加载器命名空间不同，因此同名类被两个加载器加载后是两个不同的类型，互相强转会抛 ClassCastException。这也是模组隔离的实现基础。

**4.** 注释掉访问时：只打印 `main 开始`——Lazy 类未被初始化。取消注释后：先打印 `Lazy 类被初始化了！` 再打印 `42`。说明类在**第一次主动使用（访问静态成员）时才触发初始化**，静态代码块在初始化时执行且只执行一次。

**5.** 通常有数百到上千行（一个 hello world 程序就会加载 400+ 个类：String、System、各种内部基础设施类）。这说明了 Java 标准库"开箱即用"背后是大量默默加载的基础设施类。

**6.** 会抛 `NoClassDefFoundError`/`ClassNotFoundException`：A 的代码引用 B 的类时，类加载器找不到目标类。Forge 用 dependencies 早期检查是因为：等到运行中类加载失败才崩溃，报错信息深埋在调用栈里，玩家和普通开发者根本看不懂；而启动早期按依赖表检查，可以给出"缺少模组 B"的明确提示。这体现了"把失败提前到最容易诊断的时刻"的工程思想。

## 第 03 课答案

**1.** 局部变量在栈（Stack）；`new` 出来的对象在堆（Heap）。

**2.** Minor GC 只回收年轻代，快（毫秒级）、频繁；Full GC 回收整个堆（甚至包括元空间），慢且会暂停应用线程（Stop-The-World），是造成游戏明显卡顿的主要嫌疑。

**3.** `StackOverflowError` → 栈（通常是无限递归把栈帧堆爆）；`OutOfMemoryError` → 堆（对象太多清不出空间；也可能是元空间溢出，报错信息会注明）。

**4.** 大约只有极少数活着（理论上循环结束后**一个都不需要活着**）。每次循环创建的 ItemStack 在下一次迭代时就失去了引用（变量被重新赋值），成为垃圾。这些短命对象会堆积在 Eden 区，由 Minor GC 快速批量回收——这就是"朝生暮死"，也是年轻代存在的意义。

**5.** 运行后抛出 `StackOverflowError`。`dig` 无条件地递归调用自己，每次调用在栈上压一个新栈帧，永不弹出，最终栈空间耗尽。这演示了：递归必须有终止条件；栈容量远小于堆。

**6.** 至少两个角度：① **堆太大**：Full GC 扫描范围大，单次停顿更长，"平时流畅、定期大卡"；② **瓶颈不在堆**：卡顿可能来自元空间不足（模组类太多）、CPU、磁盘 IO（区块加载）、或某模组代码低效，加内存无济于事；③ 也可能内存虽大但 GC 参数未调优。教训：性能问题要先定位（看 GC 日志/F3）再下药，盲目加内存是新手思维。

## 第 04 课答案

**1.** 依靠操作数栈。`iadd` 执行前栈顶有两个 int（操作数）；执行时弹出两个相加；执行后栈顶是它们的和（一个 int）。净效果：栈上少了一个元素。

**2.** ASM 是底层字节码操作框架（直接读写 .class 字节）；Mixin 构建在 ASM 之上，用注解式 Java 类描述补丁，再由 ASM 生成具体的字节码修改。Mixin 是"友好的上层包装"，ASM 是"底层发动机"。

**3.** 类加载（Loading）环节——字节码在从 jar 读入、进入 JVM 定义之前被转换器修改。进 JVM 的已是改造后的字节。

**4.** `square` 的字节码大致为：

```
0: iload_1      // 把参数 x（第 1 个局部变量）压栈
1: iload_1      // 再压一次 x
2: imul         // 弹出两个 x 相乘，结果压栈
3: ireturn      // 返回栈顶 int（即 x*x）
```

**5.** 还原结果：

```java
int a = 1;          // iconst_1, istore_1
if (a != 2) {       // iload_1, iconst_2, if_icmpne 跳到 10？——注意此处语义需细读
    ...
}
```

细读：`iload_1`(a=1)、`iconst_2`，`if_icmpne 10` 表示"a ≠ 2 则跳到 10"。而 1 ≠ 2 为真，所以直接跳到 10 `ireturn`，返回的是栈顶……跳转前栈上没有新值——说明这段字节码语义其实是"如果相等则做 `a+1` 再返回，不等则直接返回 a"。合理还原：

```java
int a = 1;
if (a == 2) {
    return a + 1;   // 7-9 行：iload_1, iconst_1, iadd（但其后缺少 return，简写演示）
}
return a;           // 10: ireturn
```

（本题目的是练习"跳转指令如何对应 if"，能讲清 `if_icmpne` 的跳转逻辑即可，不必苛求完全等价。）

**6.** 可能结果：① 两个补丁都成功，熔炉双倍速度且双倍燃料（兼容）；② 一个补丁覆盖了另一个的修改点，只有一个生效；③ 修改冲突导致字节码损坏，游戏崩溃。本质局限：字节码修改是"共享同一份原版代码的手术"，多个模组对同一方法动刀时缺乏协调机制——改的是同一个"公共财产"，冲突无法从机制上杜绝，只能靠模组作者小心选择注入点。这就是为什么事件 API（各模组独立收听，互不修改）永远是首选。

## 第 05 课答案

**1.** `-Xms` 堆初始大小，`-Xmx` 堆最大大小。设成相同可避免运行中堆逐步扩容造成的性能抖动（每次扩容都要向操作系统申请内存并调整内部结构）。

**2.** 出现 `Pause Full` 字样即 Full GC。停顿 900ms 意味着游戏画面冻结接近 1 秒——玩家明显感到"卡了一下"。

**3.** 堆越大，Full GC 需要扫描和整理的对象越多，单次停顿时间越长。且大堆会掩盖内存问题的早期信号，积累到 Full GC 时一次性爆发。内存应该"够用且略有富余"，不是越多越好。

**4.** F3 右上角内存百分比会缓慢爬升（新对象不断产生占用 Eden/堆），到某个阈值突然下降（发生 Minor GC 批量回收短命对象），如此锯齿状循环。这正对应分代 GC 的工作节奏。

**5.** 参考：YGC 数值 30 秒内会增加若干次（每秒数次到每几秒一次），YGCT 同步小幅增长。若看到 FGC（Full GC 次数）在短时间快速增长则异常。具体数字因机器而异，重点是学会读这两列。

**6.** 问题：① 每 tick（每秒 20 次）新建 ArrayList 和 50 个字符串——大量短命对象；② `label + n` 循环拼接产生 O(n²) 级别的临时 String。改写：

```java
private static final List<String> NAMES = new ArrayList<>();  // 静态复用，只建一次
static {
    for (int i = 0; i < 50; i++) {
        NAMES.add("marker_" + i);
    }
}

@SubscribeEvent
public static void onPlayerTick(TickEvent.PlayerTickEvent event) {
    StringBuilder sb = new StringBuilder();
    for (String n : NAMES) {
        sb.append(n).append(',');
    }
    String label = sb.toString();
}
```

（若 label 的内容本身也不变，干脆整个做成常量，tick 里什么都不做。）

**7.** 排查步骤：① 让玩家加 `-Xlog:gc*:file=gc.log` 复现问题；② 检查 gc.log 中卡顿时间点是否有 `Pause Full` 及对应停顿毫秒——若有，确认是 Full GC 停顿；③ 看回收前后内存：若 Full GC 前堆接近 Xmx 且回收效果差，说明内存不足或存在内存泄漏，先适当加内存验证；④ 若 GC 日志平静，则卡顿不在 GC——转向 F3 饼图或 spark 等工具查 CPU/ tick 耗时（如某模组的区块加载）。核心方法论：**先观测、再定位、后处置**，不猜。

## 实践项目三 · 参考结论

### 实验一

- 输出顺序：`>>> LoadTest 类初始化了` 在前，`>>> main 方法开始` 在后。**结论：类初始化（静态代码块）先于 main 方法执行**——JVM 必须先加载并初始化主类，才能调用它的 main。
- `-verbose:class` 中：`LoadTest` 的加载记录出现在大量 JDK 核心类**之后**（最后几行）；`java.lang.String` 非常靠前，因为它是 JVM 内部机制（如类加载器、字符串常量）运转的基础依赖，会被最早的一批类所依赖。
- 一个 hello world 程序通常加载 400～1000+ 个类。

### 实验二

- 正常游玩 3 分钟：通常几十次 Young GC，0～2 次 Full GC；单次 Young GC 一般 1～20ms。
- 改为 `-Xmx512M` 后：GC 明显更频繁，可能出现多次 Full GC，停顿变长——堆小了，垃圾很快堆满，GC 被迫加班，且最终可能 OOM。
- 结论：堆大小直接决定 GC 频率；甜点区之外（过小）会"GC 风暴"。

### 实验三

`pickTool` 字节码（可能因编译器版本略有差异）：

```
 0: iload_1          // 加载参数 hardness
 1: iconst_3         // 压入常数 3
 2: if_icmple 9      // hardness <= 3 则跳转到 9（对应 else 分支）← 这就是 if
 5: iconst_4         // 压入 4（钻石镐）
 6: goto 10          // 跳到返回点
 9: iconst_2         // 压入 2（铁镐）
10: ireturn          // 返回栈顶
```

关键认知：**if-else 在字节码层面 = 条件跳转（if_icmple）+ 无条件跳转（goto）**——高级语言的分支语法最终都变成"跳到哪一行"。

### 实验四

里程碑日志示例（关键词因版本而异）：JVM 信息行 → Forge `... mod scanning ...` → 你的 `LOGGER.info` 输出 → `Registry`/`loading` 阶段日志 → `Backend library: LWJGL...` / `Narrator library...`（进入主界面）。能看到自己模组的日志夹在 Forge 各阶段之间，就是对生命周期最直观的验证。

### 200 字总结（参考）

双击 runClient 后：Gradle 启动一个 JVM 进程并传入内存等参数；JVM 先加载核心类库，随后 Forge 的类加载器介入，扫描 mods 与工程里的 jar，按双亲委派加载 Minecraft 与 Forge 类；发现 @Mod 注解后用反射构造模组对象，按生命周期广播事件；所有模组的类经"加载→验证→初始化"进入 JVM，new 出的对象住进堆里；游戏主循环开始运行，JIT 逐渐把热点代码编译为机器码，GC 在后台按分代策略回收垃圾，玩家在画面上看到的每一帧，背后都是这套机制在协同工作。
