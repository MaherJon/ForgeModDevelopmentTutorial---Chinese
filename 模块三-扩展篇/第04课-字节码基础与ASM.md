## 4.1 字节码长什么样？

写一个最简单的类：

```java
public class Calc {
    public int add(int a, int b) {
        return a + b;
    }
}
```

编译后用 JDK 自带的 `javap -c Calc.class` 查看（第 01 课练习做过）：

```
public int add(int, int);
  Code:
     0: iload_1        // 把第 1 个参数（a）压入操作数栈
     1: iload_2        // 把第 2 个参数（b）压入操作数栈
     2: iadd           // 弹出两个整数相加，结果压栈
     3: ireturn        // 返回栈顶的 int
```

### 字节码的核心模型：操作数栈

JVM 是一台"基于栈的虚拟机"：指令不直接操作寄存器，而是操作一个**操作数栈**——指令从栈顶取数据、算完再放回栈顶。

> 💡 **类比**：操作数栈像一叠盘子。`iload_1` 放一个盘子上来，`iload_2` 再放一个，`iadd` 拿走最上面两个盘子、把"和"这个新盘子放上来，`ireturn` 把最上面的盘子递给调用者。

### 常见指令速认（看到能猜个大概就行）

| 指令前缀/片段 | 含义 |
|---|---|
| `iload / aload` | 加载 int / 对象引用到栈上（i=int, a=address） |
| `istore / astore` | 把栈顶存进局部变量 |
| `iadd / isub / imul` | int 加减乘 |
| `invokevirtual / invokestatic / invokespecial` | 调用普通方法 / 静态方法 / 构造或私有方法 |
| `getfield / putfield` | 读 / 写对象的字段 |
| `new`、`dup` | 创建对象、复制栈顶 |
| `ireturn / areturn / return` | 返回 int / 对象 / void |
| `iconst_0`～`iconst_5` | 把常数 0～5 压栈 |
| `if_icmpeq / goto` | 条件跳转 / 无条件跳转（if 和循环的底层） |

你不需要会写字节码——目标是**看懂大意**，理解接下来讲的修改技术。

## 4.2 为什么模组需要"改"游戏的代码？

Forge 提供了事件和注册系统，覆盖了绝大多数需求。但有些事事件做不到，比如：

- 修改原版熔炉的烧制逻辑内部细节；
- 给原版生物的 AI 里插一段新行为；
- 修原版某个方法的 bug。

原版代码是 Mojang 的，你没有源码、不能直接改。怎么办？答案是在**类加载的那一刻，修改它的字节码**——类还在"搬运途中"时被动了手脚，进 JVM 的已经是改造版。

```
原版 .class 文件 → 类加载器搬运 → 【字节码修改器动手脚】→ JVM 里的类已被改造
```

两大主流工具：

- **ASM**：Java 字节码操作框架，让你用 Java 代码读/改/写字节码。Forge 的 coremod 机制底层就是 ASM。
- **Mixin**：建立在 ASM 之上的一套更友好的"补丁"框架（Sponge 团队开发，现代 Forge/Fabric 模组大量使用）。你用带注解的普通 Java 类描述"要往哪个方法的哪个位置插什么代码"，Mixin 帮你生成字节码修改。

### Mixin 的样子（欣赏即可）

```java
@Mixin(FurnaceBlockEntity.class)   // 目标：原版熔炉
public abstract class FurnaceMixin {

    // 在原版 burn 方法的开头注入我们的代码
    @Inject(method = "burn", at = @At("HEAD"))
    private void mycoolmod$onBurn(CallbackInfo ci) {
        System.out.println("熔炉开始烧了！（我们的代码插进来了）");
    }
}
```

看不懂细节没关系，感受思想：**不碰原版源文件，却能精准地在原版方法里插入逻辑**。这就是字节码修改的威力。

## 4.3 能力越大，风险越大

字节码修改是"手术刀级"的能力，用不好就是灾难：

| 风险 | 说明 |
|---|---|
| **冲突** | 两个模组改同一个方法的同一处，可能互相覆盖 → 崩溃 |
| **脆弱** | Minecraft 升级后原版方法变了，你的补丁打歪了 → 崩溃 |
| **难调试** | 报错栈里是经过转换的类，源头难追 |

**使用原则（重要！）**：

1. 能用**事件**解决就用事件（安全、兼容）；
2. 能用**继承/包装**原版类解决就不要改字节码；
3. 万不得已才上 Mixin/ASM——它是最后的手段，不是首选的工具。

> 💡 本教程不教你写 Mixin——因为 95% 的模组永远用不到它。但理解它的原理，能让你看崩溃报告时不再一脸茫然（崩溃栈里的 `MixinApply`、`asm` 字样就是这么来的）。

## 4.4 本课小结

- JVM 是基于操作数栈的虚拟机；字节码指令围绕"压栈、运算、弹栈"工作；`javap -c` 可查看字节码。
- 字节码修改技术在**类加载过程中**改造原版类，实现事件做不到的深度修改。
- ASM 是底层字节码操作框架，Mixin 是其上更友好的补丁框架。
- 修改字节码有冲突和脆弱性风险：能事件不 Mixin，Mixin 是最后手段。
